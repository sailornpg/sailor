- 暂无。归档 feature 时由 `/harness-archive` 流程追加。

### feat-model-provider-settings — In-app Model Provider Settings（2026-09-20）

- **[架构决策]** 敏感凭据只应在特权进程解密，UI 层只接收“是否已配置”状态；空凭据更新应明确表示保留原值。（来源：应用内提供商配置）

### feat-model-picker-dialog — Model Catalog Picker Dialog（2026-09-20）

- **[流程问题]** 视觉交互验收应使用真实应用同时检查桌面和窄视口；临时服务、表单数据和测试凭据必须在验收后恢复。（来源：Electron 响应式验收）

### feat-streaming-reasoning-tools — 流式回答、推理过程与工具调用（2026-09-20）

- **[技术踩坑]** 测试直接加载 TypeScript 源码前，要确认测试运行时支持项目使用的语法与解析方式；不一致时应通过项目实际构建链加载，而不是依赖运行时的有限源码剥离能力。（来源：Node strip 模式无法加载测试目标）
- **[架构决策]** AI 界面必须区分提供商明确返回的推理摘要、应用可审计事件与模型不可访问的隐式推理；三者不能混用或用误导性文案展示。（来源：推理摘要与结构化过程视图的信息边界）
- **[架构决策]** 工具定义、编排逻辑和界面投影应分层；输入契约由执行端与展示端共享，已知工具使用专用视图，未知工具保留通用回退。（来源：工具注册表、共享 schema 和工具渲染）

### feat-split-provider-settings-dialog — 拆分设置弹窗组件结构（2026-09-20）

- **[架构决策]** 单文件超过 500 行时评估按职责拆分，按业务目录组织；共享草稿状态放在稳定的父层，避免切换页面丢失。（来源：设置弹窗拆分）

### feat-assistant-ui-migration — 聊天 UI 全量迁移至 assistant-ui（2026-09-20）

- **[流程问题]** 删除或替换组件库前，应扫描全部引用，并成对清理源码、依赖和专属样式；随后增加边界测试防止旧依赖重新进入。（来源：移除旧 AI Elements）

### 官方 Elements 视觉一致性（2026-09-21）

- 用户要求接入官方组件时，目标是官方展示效果；不得擅自追加第二组工具卡片。ToolTimeline 的官方 runtime recipe 要求替代原逐条工具与推理展示。
- Pi builtin 的 read/write/edit 参数为 file_path，不能直接套用官方示例中的 path。应依据本地安装类型映射。
- 非 layer 的全局 button font/color reset 会覆盖 Tailwind utilities；基础 reset 应放入 base layer。构建与类型检查不能代替视觉验收。

### feat-official-timeline-parity — 修正时间线重复展示并恢复官方样式（2026-09-21）

- **[架构决策]** 替换展示组件时，检查旧渲染路径是否同步停用，避免同一数据重复展示。（来源：时间线与原工具卡片同时渲染）
- **[流程问题]** 样式任务必须单独记录视觉验收结果；构建通过不能作为视觉一致的证据。（来源：预览工具连接失败，无法完成官方效果截图比对）

### feat-sidebar-active-highlight — 增强当前会话选中效果（2026-09-21）

- **[技术踩坑]** 选中态应明显区别于悬停态；需在亮暗主题下检查实际视觉效果，并验证切换选中项后旧选中态已清除。（来源：侧栏当前会话高亮）

### feat-context-breakdown-card / feat-panel-dock-skeleton — 上下文卡片 + 面板宿主骨架（2026-09-22）

- **[流程问题]** 当多个会话或协作者共用同一份状态文件时，归档、重置或批量改写前必须先确认"这份文件当前由谁维护、哪几段内容分别属于谁"，再据此决定操作顺序：让**内容的主人**拿到整文件级快照并承担重置，其余条目走轻量快照，同时不动对方会话的代码文件。原因是这类快照无法按条目拆分，顺序错了就会把别人的工作面板归到自己名下、或把对方的日志直接重置掉。（来源：两个 feature 同时待归档，而 root progress.md 的头部是另一会话的工作面板、我的日志是后面的 dated 段落）

### fix-workspace-context-submission-layout — 修复引用清空时机与消息附件行（2026-09-23）

- **[技术踩坑]** 在适配器下游做分组或筛选前，先核验转换后的运行时数据结构，并用真实转换结果测试。（来源：引用类型变化导致分组失效）
- **[技术踩坑]** 流式请求要区分“提交成功”和“生成结束”；草稿消费应绑定提交阶段，并测试生成期间新增草稿不会被清除。（来源：引用延迟清空）

### fix-files-resize-toolbar — 修复文件上下分栏拖拽并上移文件路径（2026-09-23）

- **[技术踩坑]** 拖拽计算必须统一坐标方向和单位；像素位移转换为比例时使用实际容器尺寸，并分别验证两个方向。（来源：上下分栏反向与比例换算）

### remove-file-tree-filter — 移除文件树筛选输入框（2026-09-23）

- **[流程问题]** 移除控件时，同步清理专属状态、参数、样式、文档和测试引用，并扫描残留引用。（来源：删除文件树筛选框）

### feat-unified-scrollbars — 统一应用滚动条样式（2026-09-23）

- **[技术踩坑]** 原生与自定义滚动条共存时，共享主题变量，并让全局样式保持较低优先级，避免覆盖组件隐藏原生滚动条的规则。（来源：全局 CSS 与 Radix 滚动条共存）

### feat-workspace-terminal — 右侧工作区交互终端 MVP（2026-09-24）

- **[技术踩坑]** 增量编译缓存会让「验证通过」失真：编译器的增量产物（如 `tsbuildinfo`）可能让一个早已存在的类型错误长期不被报出，直到改动被广泛共享的模块触发全量重查才突然失败。遇到这种情况先按「缓存掩盖的既有问题」处理——用回退本次改动 + 删除缓存的方式复现并确认归属，不要当成自己引入的回归；同时，声称 baseline 通过前要确认它经得起「清缓存重查」，否则任何跨模块改动都会以无关文件报错的形式阻塞验证。（来源：新增一个 `src/shared` 下的模块后，既有组件里把 `React.ElementType` 收敛成 `never` 的旧错误才暴露，阻塞了本次 checklist 的 verify）

### feat-ask-user-human-in-loop — Ask User Human-in-the-Loop Interaction（2026-09-25）

- **[技术踩坑]** 流式 UI 数据进入副作用时，应使用稳定的值签名或明确版本号作为依赖；不要直接依赖每次流式更新都会重建的对象，否则副作用中的状态更新可能形成循环。（来源：问答卡片的流式参数更新导致 React 无限更新和白屏）
- **[技术踩坑]** 异步快照存在短暂空窗时，应在同一操作上下文内保留最后有效状态，并只在明确的上下文切换或终态确认后卸载 UI。（来源：计划浮层在工作区快照更新期间闪烁消失）

### fix-todo-approval-lifecycle — 审批续跑期间 TodoList 持续显示（2026-09-25）

- **[架构决策]** 瞬态任务面板的可见性应由“执行仍在进行”与“是否存在待处理交互”共同决定；即使步骤已全部完成，只要交互尚未结束就保持面板，终态退场还要用幂等保护确保只执行一次。（来源：工具权限等待期间计划提前退场，以及快照刷新重复触发退场）
- **[流程问题]** 涉及流式执行、审批和会话切换的 UI 生命周期修改，验证必须覆盖真实组件挂载和连续状态转换，包括 StrictMode、切换会话、快照短暂缺失、历史恢复和终态退场。（来源：单元测试无法覆盖的 React/Electron 生命周期闪烁）

### feat-define-toolkit-refactor-implementation — Sailor 工具 UI 注册表重构实施（2026-09-25）

- **[技术踩坑]** 流式消息的中间态必须按参数可能缺失、结果可能非法处理；渲染层对未完成结构做安全降级，避免单个消息片段导致整棵 UI 崩溃。（来源：工具参数未完整时触发 renderer 异常和白屏）
- **[架构决策]** 运行时 UI 注册表应保持单一稳定实例，并由生命周期负责注册和清理；StrictMode、卸载、重新挂载都要验证不会累积注册或重复渲染。（来源：模块级 toolkit 与 Provider/Thread 注册清理）
- **[流程问题]** 真实 Electron 验收应在 feature checklist 创建时登记专用 smoke 路径；遇到打包或 CDP 环境阻塞时要单独记录 blocker，不能用通用 Node 测试替代桌面证据。（来源：toolkit Electron fixture、packaged smoke 超时与后续复验）
- **[技术踩坑]** 涉及流式回答的 UI 查询只能绑定当前消息或当前运行上下文，不能从历史消息回扫并复用旧交互标识。（来源：旧 ask_user 卡片携带新 runId 提交导致 pending interaction 不存在）

### feat-composer-thinking-menu-polish / feat-composer-thinking-menu-minimal — Composer thinking 菜单视觉与滚动优化 + 极简化（2026-09-26）

- **[技术踩坑]** 浮层里「长列表 + 常驻操作区」的布局，滚动容器必须只包住列表本身，操作区放在滚动容器之外；否则列表滚动会把操作区一起滚走，出现「列表越长、关键控件越不可见」的问题。改这类浮层时先确认滚动边界落在哪个元素上。（来源：统一模型/thinking 菜单把模型列表做成独立滚动区、thinking 控制区固定可见）

### feat-composer-default-permission-unified-thinking — Composer 默认工作区执行与统一 thinking 选择（2026-09-26）

- **[架构决策]** 引入分档策略（权限档、粒度档、自动化档等）时，「新对象默认档」和「旧数据缺失字段的迁移档」都属于产品决策，要在 spec 阶段就和用户确认，不要自行选最保守值；否则下一轮迭代很可能整体反转默认，连带改掉持久化回退、运行上下文和 UI 文案。（来源：工作区权限默认档先定为「只读」，下一个 feature 立即改为「默认执行」）

### fix-composer-slash-keyboard-navigation — Composer Slash Keyboard Navigation（2026-09-27）

- **[技术踩坑]** 桌面/集成 smoke 的 fixture 必须直接复用被测的生产渲染路径或组件；在 fixture 里复制一份实现，测试证明的是副本正确而非产品正确，生产路径仍可能保持错误。（来源：Electron fixture 与生产 Composer 共享同一份修正后的列表渲染器，而不是各写一份）

### feat-composer-pi-tui-actions — Composer Pi TUI Actions（2026-09-27）

- **[架构决策]** 一个命令或能力注册表若混合了多种执行语义（字面 prompt、UI 动作、宿主操作等），必须显式建模语义类型并在分发点按类型路由：只有字面类进入 prompt 通道，动作类走明确的 UI/IPC 映射且不伪造审批记录。不要用字符串前缀或命名约定推断语义，否则每新增一类命令都要重新猜边界。（来源：Pi TUI 命令映射为 Sailor action，Skill 命令保持 literal）

### feat-chat-file-diff-review — 会话文件变更与只读审查（2026-09-29）

- **[架构决策]** 摘要/列表类接口只返回计数与元信息，正文和大字段由详情调用按需单独取；否则一次列表调用就把正文重复搬运过进程边界，负载与序列化开销随数据量线性放大。（来源：文件审查摘要 IPC 携带 diff 正文导致响应膨胀，改为摘要省略正文、详情单独请求）
- **[架构决策]** 跨进程共享的契约类型必须放在双方都能引用的中立层；main 专属（依赖 Node/Electron）的类型不可被共享层或渲染层引用，类型检查是发现这类越界的信号。（来源：shared 引用 main 类型导致类型检查失败，纯数据类型被移入 `src/shared/fileReview.ts`）

### fix-cross-platform-terminal-shell — 终端按宿主平台选择 shell 与关闭方式（2026-09-28）

- **[流程问题]** 依赖真实进程、终端或时序的端到端冒烟不是幂等的；不要在同一验证轮里对同一冒烟连续执行两次，出现差异时先按环境或残留状态定位，而不是直接判为回归。（来源：verifier 连续执行同一桌面冒烟，第二次仅 38/47 通过，最终单次复验 47/47）

### fix-streaming-persistence-storm — 流式期间的持久化与广播节流（2026-09-30）

- **[架构决策]** 由高频事件（流式分片等）驱动的落盘与跨进程广播必须按时间窗合并，并在终态强制 flush 一次；合并只作用于持久化与通知，逐条下发的用户可见数据流不受影响。断言写成「次数有上限 / 不随事件数增长」，而不是某个固定次数，否则阈值一调测试就假失败。（来源：流式期间每 chunk 全量写盘并广播，改为按窗口合并后实测 40 分片 → 3 次、200 分片 → 3 次，UI 仍收到 40 / 200 条增量）
- **[架构决策]** 「加载期校验」不能放在每次变更路径上：若每次写入都对整份数据 read + parse + schema 校验再整体替换，单次操作成本随数据规模增长并拖垮上游。应在加载时校验一次、在内存持有已验证状态，落盘只做序列化与原子替换；同时必须保持既有的并发写入语义（如旧写入不得覆盖新写入）与「损坏数据拒绝覆盖」。（来源：工作区存储的写入路径重复重读重校验，改为内存态持有 + 加载期校验一次）

### fix-thread-scroll-arbitration — 流式滚动抖动与跟随失锁修复（2026-09-30）

- **[架构决策]** 涉及布局度量的交互裁决（是否跟随、是否暂停、是否恢复）应抽成不依赖 DOM 的纯函数，组件只负责把观测到的事件转发进去；分支由 Node 单测覆盖，组件接线由静态回归测试守护，真实几何交给桌面冒烟验收。这样「几何相关行为」才有无需布局引擎的可回归证据。（来源：滚动跟随判定抽成纯状态机 + 静态接线回归 + Electron 冒烟三层分工）
- **[技术踩坑]** 同一个布局/滚动属性若有多个写入者（框架自动滚动、平台自动行为、程序化写入）同时改，必然出现高频互抢：应显式关闭平台提供的自动行为（如滚动容器的 `overflow-anchor`），并给程序化写入打标记，使这些事件不参与用户意图判定——即「同一属性只留一个裁决者」。（来源：viewport 被 assistant-ui、滚动锚定与本地上滚判定三方争抢 scrollTop，表现为抖动与跟随失锁）
- **[技术踩坑]** TDD 的 Red 阶段若某个断言构造出的前置状态在现实中不可能出现，先怀疑测试预期本身，而不是加实现去迎合它；先证明该状态的可达性，再写实现。（来源：两处用例分别用了会改变度量的「无变化」事件、以及「跟随中却远离底部」的不可能状态，修正测试后实现语义才收敛）
- **[流程问题]** 时序敏感的 UI 测量必须自带「激励有效性」断言：采样前等布局与补间动画稳定，并用例断言「改动确实产生了预期幅度的效果」（如塌缩必须让滚动盒缩小超过阈值），否则测到的是假漂移；同时避免每个 tick 都被重建的锚点节点进入测量路径。（来源：塌缩激励被同帧内容增长抵消、平滑滚动补间在暂停后仍在跑、锚点段落每帧重建，三处都产生过假漂移）
