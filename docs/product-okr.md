# Sailor 产品规划与 OKR

> 版本：v1.1
>
> 更新时间：2026-09-22
>
> 文档性质：产品方向与路线规划，不直接替代 `.agent-harness/feature_list.json` 中的实现状态。

## 1. 产品定位

Sailor 是一个**本地优先、可控自治、能够完成并验证真实代码任务的桌面编程 Agent**。

它的核心承诺是：

> 用户给出目标后，Sailor 能理解当前项目，自己制定计划，按风险边界执行修改和验证，在需要介入时暂停，并最终交付可审查、可复现的结果证据。

通用个人 Agent 是第二能力层，优先服务于代码、文件、文档、搜索和项目工作。它不应在核心编程闭环稳定前扩展为覆盖所有生活事务的通用助手。

## 2. 当前判断

### 2.1 已有优势

- Electron + React + AI SDK + assistant-ui 的本地桌面基础。
- 项目与会话持久化、多个会话并行运行、后台完成和未读状态。
- Pi 原生读写工具、Skills、自动上下文压缩和 checkpoint。
- 写入、编辑、命令执行的主进程审批边界。
- 多 Provider、模型目录、上下文用量、推理摘要和附件解析。
- Web 搜索、引用、Conversation Map、聊天归档和面板宿主基础。

### 2.2 当前主要缺口

当前系统仍更接近“带工具的聊天工作区”，距离可托付的任务 Agent 还缺三段闭环：

1. **不能在应用内完成真实验证**：当前虚拟 bash 不能运行本机的 pnpm、Node、编译器或测试框架。
2. **变更审查不完整**：文件树、聚合变更、Git diff 和验收视图仍不完整或处于占位状态。
3. **长任务恢复不完整**：应用重启后不能从断点继续流，审批和当前回合会失效。

因此下一阶段不以增加模型、工具数量或面板数量为主要目标，而以“任务从目标到证据的闭环”为主线。

## 3. 用户与使用场景

### 3.1 首要用户

个人开发者，主要在自己的本地项目中使用 Sailor 完成日常工程任务：

- 修复一个缺陷。
- 实现一个小到中等规模的功能。
- 阅读和梳理陌生代码。
- 执行重构并验证回归。
- 根据文档、Issue 或搜索结果修改项目。
- 在提交前检查改动和测试结果。

### 3.2 次要场景

- 读取和分析 PDF、Word、Excel、CSV 等项目附件。
- 查询网页资料并带来源引用地加入任务。
- 维护项目内的规则、命令和工作流程。
- 记录用户偏好，减少重复设置。

### 3.3 暂不作为主场景

- 多人实时协作和团队权限。
- 跨设备云端同步。
- 面向所有日常事务的通用助理。
- 无边界的浏览器自动化和外部系统操作。

## 4. 产品原则

1. **结果优先**：一次可靠完成并验证的任务，比新增十个无法形成闭环的工具更有价值。
2. **风险分级**：读操作自动执行；写入、删除、网络和高风险命令具有明确审批和可见影响范围。
3. **当前任务内自治**：允许 Agent 在用户给定预算内连续推进，但不引入永久隐式授权。
4. **证据优先**：任务结论必须能关联到具体变更、命令和验证结果。
5. **事实来自真实来源**：项目规则优先读取 README、AGENTS.md、CLAUDE.md 和实际配置，不复制一份容易过期的隐式项目知识。
6. **可恢复而非重放**：恢复任务时沿用已保存的状态，不重复执行已经完成的写入或命令。
7. **能力边界可解释**：无法执行、无法验证或权限不足时，明确告诉用户原因，不用成功占位数据掩盖限制。

## 5. 北极星指标与护栏指标

### 5.1 北极星指标

**可验证任务完成率**：用户定义的代码任务中，同时满足“变更达到目标、验证命令执行完成、结果证据可审查”的任务比例。

建议统计范围：只纳入用户明确开始的任务，不把闲聊和只读问答计入分母。

### 5.2 关键结果指标

- **KR-A：** 至少 80% 的已开始代码任务能生成结构化计划，并在完成时留下任务摘要。
- **KR-B：** 至少 70% 的可验证代码任务在 Sailor 内完成至少一次测试、构建或 lint 验证。
- **KR-C：** 至少 90% 的已完成任务能展示受影响文件、变更摘要和验证结果。
- **KR-D：** 长任务在应用重启后的恢复成功率达到 95%，且不重复已确认的写入操作。
- **KR-E：** 任务完成后被用户发现的“错误完成”比例低于 5%。
- **KR-F：** 在风险边界不变的情况下，平均每个任务的人工审批次数逐季下降。

### 5.3 护栏指标

- 未经用户批准的写入、删除或高风险命令：0 次。
- 越出选定工作区或读取敏感凭据路径：0 次。
- 恢复任务重复执行已完成写入：0 次。
- 用户无法解释某次修改来源的任务比例持续下降。
- Agent 运行期间发生无上下文错误、无操作建议的失败必须可定位。

## 6. 年度目标（O）

### O1：把 Sailor 从聊天式工具工作区升级为可恢复的任务执行系统

用户能够看到 Agent 的计划、当前步骤、暂停原因、剩余预算和最终结果；长任务可暂停、恢复和取消。

**关键结果：**

- KR1.1：建立统一的任务状态机：`planned`、`running`、`waiting_approval`、`verifying`、`paused`、`completed`、`failed`、`cancelled`。
- KR1.2：每个代码任务都能生成、更新和持久化 todo/plan；计划步骤拥有稳定 ID 和状态。
- KR1.3：实现应用重启后的 checkpoint 恢复，恢复过程不重放已完成的工具调用。
- KR1.4：任务支持时间、命令次数、文件范围和风险级别预算，预算耗尽自动暂停。
- KR1.5：失败、超时、取消和保存失败都有可操作的恢复路径。

### O2：建立受控的本机执行与验证闭环

用户能够批准在所选项目内运行测试、构建和 lint，Agent 能读取结果并据此继续修复。

**关键结果：**

- KR2.1：提供主进程托管的受控命令执行能力，renderer 不获得通用 Node/fs 权限。
- KR2.2：每次命令展示命令文本、工作目录、预计影响、环境限制和超时设置。
- KR2.3：实现风险分级授权：读操作自动，低风险验证可在当前任务内临时授权，高风险操作逐次批准。
- KR2.4：支持取消、超时、输出截断、退出码、信号和常见启动失败的结构化反馈。
- KR2.5：测试、构建和 lint 的结果能被 Agent 继续消费，并成为最终任务证据的一部分。
- KR2.6：明确网络访问、敏感路径、符号链接和工作区越界规则，并为每类拒绝提供可理解原因。

### O3：让用户能快速审查并接受 Agent 的变更

用户无需阅读完整对话，就能判断 Agent 改了什么、为什么改、是否验证过、还有什么风险。

**关键结果：**

- KR3.1：提供真实的变更文件列表和聚合 diff 视图。
- KR3.2：将每个变更关联到计划步骤、工具调用和验证命令。
- KR3.3：支持按文件查看修改前后内容、风险提示和未解决问题。
- KR3.4：任务完成摘要包含目标、变更、验证、失败重试和剩余风险。
- KR3.5：在可用场景下提供回滚或安全撤销入口；不能回滚时明确告知用户手动恢复方式。

### O4：建立透明、可控的个人记忆能力

记忆首先减少重复配置，而不是替代项目真实文件或悄悄积累不可解释的上下文。

**关键结果：**

- KR4.1：支持用户明确保存和编辑个人偏好，例如审批习惯、输出风格和常用工作方式。
- KR4.2：跨项目记忆默认关闭，开启后按来源、范围和更新时间展示。
- KR4.3：每条记忆都可查看、修改、删除和停用。
- KR4.4：项目规则继续以 README、AGENTS.md、CLAUDE.md 和配置文件为优先来源，不自动复制为第二份真相。
- KR4.5：记忆冲突时显示冲突来源，并让当前项目文件优先于个人记忆。

### O5：让 Sailor 的任务全过程透明、可观测、可追溯

用户可以通过持久化执行轨迹，查看每个关键步骤的输入、输出、状态、耗时、权限依据和实际影响，定位失败原因，并核对任务恢复与最终交付的证据。Observability 是与 O1 同期建设的 P0 基础能力，目标编号不代表实施顺序。

**关键结果：**

- KR5.1：建立版本化事件目录，覆盖任务生命周期、计划调整、上下文与 Skill/记忆加载、模型调用、工具操作、审批、压缩、checkpoint、恢复和验证。每个已注册执行入口在验收场景中都有开始记录及终态或明确的中断/结果未知状态，覆盖率目标为 100%；后续新增入口必须同步纳入。
- KR5.2：轨迹通过稳定的任务 ID 关联跨重启运行，并关联 run、计划步骤、模型调用、工具调用、审批和产物。所有由 Sailor 执行的写入均能追溯授权依据和执行结果；读取规则文件与实际将其加入模型上下文应分别记录。
- KR5.3：提供应用内「轨迹」面板，支持实时调用树、步骤详情、输入输出、耗时、失败筛选、搜索及跳转到聊天、文件变更和验证证据；耗时区分模型等待、工具执行、审批等待和重试。
- KR5.4：本地默认保存关键轨迹，应用重启后仍可查询。覆盖正常结束、拒绝审批、取消、超时、崩溃和存储失败的验收场景；缺失结束记录的步骤不能显示为成功，保存失败和采集缺口必须对用户可见。
- KR5.5：所有标记为“已验证”的任务结论均能关联实际验证调用及结果。模型自述、工具执行事实和未确认副作用明确区分；提供商未返回的用量与内部推理不推算、不补造。
- KR5.6：提供保存范围、保留期限、容量管理、删除和脱敏导出能力；密钥不进入轨迹，输入输出的脱敏、截断和未采集情况均有明确标记。外部遥测导出由用户显式开启。
- KR5.7：历史轨迹查看和回放只读，不触发模型调用或工具执行。崩溃发生在副作用与结果落盘之间时，恢复先核对实际状态；故障注入验收不得因查看或恢复轨迹重复执行已完成操作。

**覆盖边界与验收口径：**

- 首期覆盖 Sailor 托管的任务操作；模型配置、权限与记忆等影响执行的用户操作也记录变更事件，不记录密钥值或无关界面点击。
- 采集以 Harness/Pi 与主进程执行端事件为依据，不依赖聊天文本推断操作。已有开发调试 reporter 可作为接入基础，不能直接视为生产轨迹已完成。
- 本机命令的子进程、网络请求和文件副作用需要额外观测能力；未覆盖部分必须标明未知，不能以命令启动记录宣称整个操作系统透明。
- 轨迹覆盖率按事件目录及真实成功、失败、取消和恢复场景验收；轨迹用于解释恢复过程，不能替代恢复所需的执行状态与 checkpoint。

## 7. 功能路线

### P0：任务可靠性基础

目标：先让长任务有秩序、有状态、可恢复。

- 任务计划与 todo 数据结构。
- 可见的计划面板和当前步骤状态。
- checkpoint、恢复、暂停、取消和失败重试。
- 任务预算和自动暂停。
- 任务完成、失败和需要介入的通知。
- 统一的运行事件和审计日志。
- O5 轨迹基础：执行端采集、关联 ID、脱敏、本地持久化和保存失败提示。
- 应用内轨迹面板、步骤详情、历史查询，以及计划/checkpoint/重试/恢复的关联展示。

验收重点：应用重启后能从最后一个安全 checkpoint 继续；已完成写入不会被重复执行；审批失效时任务能清楚停在等待状态。

轨迹验收重点：关键执行入口有可追溯记录；中断和未知结果不会显示为成功；重启后历史仍可查；回放不执行操作。P1 接入命令与验证证据，P2 接入 diff 与交付证据，P3-P4 新能力沿用同一事件契约。

### P1：受控执行与验证

目标：让 Sailor 可以真正验证自己做出的修改。

- 受控本机命令执行。
- 测试、构建、lint 的命令模板和结果解析。
- 风险分级审批和当前任务临时授权。
- 超时、取消、输出上限和失败原因。
- 工作区、敏感路径和网络边界。
- 验证失败后的自动修复回合。

验收重点：Agent 不能在未授权时执行高风险命令；失败结果能回到计划步骤；用户能区分“命令没启动”“命令失败”和“验证未配置”。

### P2：变更审查与交付

目标：让用户能在短时间内审查并接受结果。

- Git diff 和文件变更聚合。
- 文件树与变更文件联动。
- 变更摘要、验证证据和风险摘要。
- 审批记录、命令结果和文件改动的关联。
- 可恢复的撤销或回滚流程。

验收重点：用户不打开完整聊天，也能回答“改了什么、为什么改、验证了吗、还有什么问题”。

### P3：个人偏好与跨项目记忆

目标：减少重复配置，同时保持来源透明。

- 偏好设置和显式保存入口。
- 跨项目记忆的开关、范围和删除。
- 记忆来源和冲突提示。
- 从历史任务中提议候选偏好，但不自动写入。

验收重点：用户能理解每一条记忆的来源，并能在一次操作内停用或删除。

### P4：代码相关的通用 Agent 能力

目标：在核心编程闭环稳定后扩展工作范围。

- 文档、网页和代码资料的联合研究。
- Issue、设计文档和附件到代码任务的转换。
- 只读浏览器和引用结果的任务化使用。
- 代码之外的文件整理和分析，但仍在明确工作区边界内。

验收重点：新增通用能力必须提升代码任务成功率或减少上下文切换，不能只增加工具数量。

## 8. 长任务默认交互

一次任务建议遵循以下状态流：

```text
用户目标
  -> Agent 读取项目事实
  -> Agent 生成计划与预算
  -> 用户查看计划（可修改）
  -> Agent 自主执行低风险步骤
  -> 高风险操作进入临时审批
  -> 运行测试 / 构建 / lint
  -> 失败则回到计划并继续修复
  -> 生成 checkpoint 与交付摘要
  -> 用户审查 diff 和证据
```

默认暂停条件：

- 目标存在无法自行消解的歧义。
- 即将超出文件、命令、时间或风险预算。
- 命令涉及删除、外部网络、敏感路径或未声明副作用。
- 验证失败且继续尝试需要改变原定策略。
- checkpoint 保存失败或恢复状态不可信。

## 9. 架构与安全要求

- 模型、凭据和执行能力继续只位于 Electron main process。
- renderer 只通过窄 preload IPC 获取任务状态、审批和结果。
- 所有路径继续通过工作区作用域校验，拒绝绝对路径、越界、敏感文件和不安全符号链接。
- 本机命令执行不能伪装成“命令白名单就等于沙箱”；必须明确工作目录、环境、网络和副作用边界。
- 审批记录绑定 chat、run、call 和工具名称，临时授权过期后不可复用。
- 外部网页、模型输出、项目文件和命令输出均视为不可信输入，跨边界使用 schema/type 校验。
- 任务恢复使用事件和 checkpoint，不重新执行历史工具调用。
- 真实状态优先于占位面板；能力未接入时展示明确不可用原因。

## 10. 明确暂缓

在 P0-P2 完成并达到指标前，暂不投入以下方向：

- 云端沙箱和远程工作区同步。
- 多人协作、共享会话和团队权限。
- 自动发现机器上的所有项目。
- 跨工作区移动聊天和复杂全局聊天管理。
- 永久项目信任或无审批自主执行。
- 面向生活事务的邮件、日历、支付等广泛自动化。
- 多 Agent 编排和复杂角色系统。
- 仅为了扩大列表而新增 Provider、工具或面板。

## 11. 主要风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 本机执行扩大攻击面 | 命令可修改项目或访问外部资源 | 主进程执行、风险分级、临时授权、路径和网络边界、完整审计 |
| 长任务状态不一致 | 重启后重复写入或丢失进度 | 稳定事件 ID、checkpoint、幂等恢复、失效审批清理 |
| 计划变成装饰 | Agent 显示计划但不按计划推进 | 每个步骤必须关联工具调用、验证结果和状态转移 |
| 记忆污染 | 旧偏好覆盖当前项目事实 | 显式来源、范围和时间；项目文件优先；默认不自动写入 |
| 功能面扩张过快 | 工具很多但完成率不提高 | 所有新能力绑定北极星指标和真实任务案例 |
| 验证结果不可信 | 命令失败被误报为成功 | 保留退出码、信号、原始输出摘要和环境信息 |

## 12. 决策门槛

每个后续 feature 在进入实现前，至少回答：

1. 它提升的是任务完成率、验证可信度、恢复能力还是审查效率？
2. 它是否让用户更清楚 Agent 做了什么和为什么做？
3. 它的权限、数据来源、失败恢复和取消语义是否明确？
4. 它是否可以在现有 main/preload/renderer 分层内实现？
5. 它是否有可观察的验收证据，而不是只依赖模型主观描述？

若不能回答上述问题，应先补设计或延后，而不是直接加入 feature 列表。
